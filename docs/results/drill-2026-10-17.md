## Follow-ups (written after the run)

The drill found three problems in the release tooling. Each is fixed in the same commit as this report:

1. **The eval gate let the bad release through.** v1.5.0 passed the gate at exactly the 95% threshold
   (19/20; the one failure was a loop on `total-math`). The 10% traffic step caught it, but customers
   saw it first. Fix: the gate now also requires **zero guardrail trips** on the golden set
   (`eval_gate.max_guardrail_trips: 0`). Verification run at 10:16:39, same release, same 95% pass rate:
   rejected at the gate, before any traffic (`eval_gate passed=False pass_rate=0.95 guardrail_trips=1`,
   rollback 31s after start, 0 customer requests).
2. **A leftover alert failed the second v1.5.0 canary in 43s.** The `AgentLoopRateHigh` and
   `AgentCanaryFailureRegression` alerts were still firing from the first attempt (5-minute windows).
   The verdict was right for this release, but the same leftover would have failed an unrelated next
   release. Fix: the controller only counts critical alerts that carry this canary's release (or no
   release label) and became active after this canary started (`canary.analysis.canary_alerts`); the
   per-release alert rules are joined with `agent_build_info`, so they stop for a release that is no
   longer running (promtool test included).
3. **Pages arrived after the rollback.** `AgentLoopRateHigh` paged at 10:10:54, 93s after the controller
   had already rolled the canary back (10:09:21), and `AgentFailureRateHigh` paged at 10:12:08 for a
   release that had stopped serving. Fix: Alertmanager routes `track="canary"` alerts to chat (the
   controller owns that remediation); only stable pages a human. `make test-rules` asserts the routing.

Also found while reading the dashboards for this report: per-track ratio panels summed per-release
ratios, so during the promotion stable's p95, cost/request and model calls/request appeared to double.
The panels now compute per-track ratios from the raw counters.

The drill script's own bug: `kill -INT` does not stop a background job of a non-interactive shell, so the
load generator kept running and was stopped by hand at 10:15:48 (the report window ends there). Fixed
(`kill -TERM`, handled by the load generator).
